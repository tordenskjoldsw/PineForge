# v0.2.0 — Platform Foundation

`v0.1.0` is the immutable OTA proof-of-concept baseline. The purpose of
`v0.2.0` is to turn that hardware bring-up into a maintainable firmware
platform before broad feature development begins.

## Product direction

PineForge is an embedded firmware platform, not a general-purpose operating
system. Embassy schedules single-owner hardware tasks; services own product
policy; a hardware-independent application model owns navigation; screens
render state without directly accessing peripherals.

The first product slice is:

```text
Watchface
    ├── Quick settings
    ├── Application launcher
    └── Settings
            └── Firmware and recovery
```

Notifications and health applications follow only after this slice works
through navigation, persistence, sleep/wake, and OTA.

## Navigation contract

- The watchface is the root and cannot be popped.
- A horizontal gesture opens the application launcher.
- A vertical gesture opens quick settings.
- A consistent back gesture pops one screen: a screen is left by the reverse
  of the gesture that opened it.
- The side button pops one screen too, so a screen reached by a tap can be
  left without an on-screen control. It is an addition to the back gesture,
  not a replacement for it.
- A press on a sleeping watch wakes it and does nothing else.
- Holding the side button for two seconds resets the watch. The reset must
  stay reachable without help from the display task, and a software restart on
  the firmware screen exists so the button is not the only reboot path.
- Holding the button during boot still reaches the bootloader's minimal
  recovery image; that path is bootloader-side and unaffected by firmware.
- Pairing, DFU, confirmation, and fatal recovery prompts are system modals
  above the screen stack.
- A modal consumes the input that dismisses it; that input never also
  navigates the underlying screen.

Exact gesture directions remain a UX decision to validate on hardware before
they become a compatibility contract.

## Lifecycle contract

Each screen has:

- persistent model state owned outside rendering where appropriate;
- an explicit enter/leave boundary for starting and stopping services;
- hardware-independent event handling;
- full redraw after wake;
- bounded partial redraw while active;
- no direct ownership of BLE, sensors, flash, or display hardware.

Background services continue independently of the visible screen unless an
explicit power or privacy policy suspends them.

## Memory budgets

Production targets:

| Resource | Hard CI limit | v0.2 target |
|---|---:|---:|
| Static RAM | 48 KiB | no more than 44 KiB |
| Runtime/stack reserve | 16 KiB minimum | 20 KiB minimum |
| Flash | 384 KiB | no more than 360 KiB |

Subsystem guidance:

- display transition scratch: no more than 8 KiB;
- BLE packet pool: change only with an end-to-end OTA hardware test;
- DFU queue: change only with an end-to-end OTA hardware test;
- new channels must document element size and capacity;
- large values must not remain live across an `await` without a measured need.

The first reduction narrows the transition stripe from 24 to 16 pixels,
reducing its static buffer from 11.25 KiB to 7.5 KiB. This trades five
additional display transactions per transition for 3.75 KiB of RAM.

Slide transitions are gated by the `ui-animations` Cargo feature and are part
of the normal production default. Memory experiments can disable default
features and re-enable only BLE, without changing the navigation contract:

```bash
cargo build --release --no-default-features --features ble
```

`scripts/build-dfu.sh` builds this production profile by default. Feature
variants are opt-in through `PINEFORGE_FEATURES` and must be labeled as
diagnostic artifacts; routine OTA validation always uses the production image.

## Milestone work

### A. Foundation and measurement

- preserve `v0.1.0` tag and release unchanged;
- record production and diagnostics section sizes in CI;
- reduce production static RAM below 44 KiB where hardware behavior permits;
- document the largest static allocations and task futures;
- retain successful format, Clippy, host-test, flash-budget, and RAM-budget
  gates.

### B. Navigation shell

- add an application launcher screen;
- add a quick-settings screen;
- make navigation rules explicit in the pure state crate;
- centralize system-modal ownership;
- add host tests for root, push, back, modal dismissal, and sleep/wake redraw.

### C. Product slice

- polished watchface;
- launcher to settings and back;
- brightness and timeout controls with persistence;
- battery and BLE status;
- firmware confirmation, OTA progress, failure, and recovery UI;
- complete hardware test covering boot, navigation, sleep/wake, settings
  persistence, OTA, and recovery.

## Acceptance criteria

`v0.2.0` is complete when:

1. production static RAM is at or below 44 KiB with at least 20 KiB left for
   runtime stack growth;
2. the watchface, launcher, quick settings, and settings use one documented
   navigation model;
3. pairing and DFU modals cannot be overwritten by background events;
4. sleep/wake restores the active screen correctly;
5. settings survive reboot;
6. the complete Gadgetbridge OTA flow still reaches 100%, validates, and
   boots the staged image on hardware;
7. the red-logo minimal InfiniTime recovery path remains documented and
   usable;
8. CI passes formatting, strict Clippy, host tests, release builds, and size
   budgets.

## Explicitly deferred

- final visual branding and pixel-perfect component styling;
- notifications;
- alarms and timers;
- production heart-rate algorithms;
- weather and music control;
- external resource packs;
- aggressive BLE/DFU buffer reductions without hardware evidence.
