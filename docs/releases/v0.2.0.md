# PineForge v0.2.0 — Platform Foundation

> [!CAUTION]
> This is experimental firmware, not a production release. It may require
> rollback or recovery and could leave a sealed PineTime unusable. Keep an
> official InfiniTime DFU package available and read the installation and
> recovery instructions before flashing.

PineForge v0.1.0 proved the OTA path. v0.2.0 turns that bring-up into a
platform: product policy lives in a host-tested state crate, screens render
state without touching hardware, and the paths a sealed watch needs to recover
itself no longer depend on a single button press.

## Highlights

**A software restart, and firmware confirmation on its own screen.** Swipe
right from the watchface reaches firmware confirmation and a restart that does
not need the side button. The value column names the consequence rather than
the action: while an image is unconfirmed a restart is a rollback to the
previous firmware, so it reads `ROLLBACK` until confirmed and `REBOOT`
afterwards. The wording changing is also the confirmation that `image_ok`
reached flash.

**The side button is the back button.** A press pops one screen, holding it for
two seconds resets the watch. Until now the reset was unconditional because it
was the only way out of a hung image; the software restart removed that
dependency. The reset still fires from the timer while the button is held
rather than on release, and the back event is offered to the UI rather than
awaited, so a stalled display task cannot take the reset with it. A press on a
sleeping watch only wakes it. Holding the button during boot still reaches the
bootloader's minimal recovery image.

**BLE pairing survives reboots and updates.** Bond keys persist in their own
external-flash sector with a CRC32-checked record, connections are marked
bondable so a bond is produced at all, and the bond is installed into the
stack before advertising starts. The device address comes from the factory-
programmed `FICR` word, so identity is stable across reboots, rollbacks and
firmware versions: after an OTA the phone reconnects on its own.

The record also carries a tag naming the BLE-stack layout that wrote it,
derived from the locked dependency version at build time. `postcard` is not
self-describing, so without the tag an update that changed the payload layout
would read the old bytes as valid and install keys the phone cannot use —
which on Android needs a manual unpair to escape. A record tagged otherwise is
now discarded in favour of re-pairing.

### Also in this release

- system modals (pairing, DFU progress, DFU failure, first-boot format) are
  modelled as testable product policy with an explicit precedence, and a modal
  consumes the input that dismisses it instead of also navigating behind it;
- navigation is a gesture contract in the pure crate: a screen is left by the
  reverse of the gesture that opened it, and a route table is the only place
  that knows where a gesture leads;
- watchface readings are separated from the face drawing them, with a face
  registry and a persisted choice;
- resilient external-flash storage with power-loss-safe formatting, versioned
  and checksummed settings across two slots, and background heart rate;
- phone notifications are received over the Alert Notification Service and
  counted on the watchface;
- OTA throughput improved by overlapping flash writes with packet receipts and
  pre-erasing one sector ahead;
- date on the watchface, a medium backlight level, and a paginated list model
  for the menus still to come.

## Memory

Measured for the production image in this release:

| Resource | This release | Hard limit |
|---|---:|---:|
| Flash | 354,180 B | 393,216 B |
| Static RAM | 45,332 B | 49,152 B |
| Free for stack growth | 20,196 B | 16,384 B minimum |

The four largest static allocations are the BLE task future (11,168 B), the
BLE packet pool (8,068 B), the display transition scratch (7,704 B) and the
Nordic controller memory (4,728 B) — together 70% of static RAM. Every screen
in the firmware shares the 544 B display-task future.

## Not yet in this release

`docs/V0.2-PLATFORM-FOUNDATION.md` defines acceptance criteria this release
does not fully meet, and they carry forward:

- the application launcher and quick-settings screens do not exist yet, so the
  gesture map is recorded but only partly routed. Two provisional routes keep
  today's screens reachable: swipe down opens display settings, swipe right the
  firmware screen. Both go away once the launcher exists;
- static RAM is 45,332 B against the 44 KiB design target, and 20,196 B remain
  for stack growth against a 20 KiB goal. Both are within the CI limits above
  but short of the stricter targets;
- notifications have no screen of their own; reception works and the count is
  visible on the watchface.

## Known limitations

- OTA transfer speed is slower than stock InfiniTime and is bounded by the BLE
  link layer rather than by flash.
- PineForge remains incomplete and is intended for development and hardware
  testing.
- The release has not been validated across all PineTime hardware or
  bootloader revisions.
- Recovery from a failed update may be difficult on a sealed watch.

## Installation

1. Fully charge the watch.
2. Save a known-good official InfiniTime DFU ZIP on the phone.
3. Read `GETTING-STARTED.md` and the sealed-device testing guide.
4. Download `pineforge-mcuboot-app-dfu-0.2.0.zip` from this release.
5. Verify its SHA-256 checksum against the value below.
6. Open the ZIP with Gadgetbridge's firmware installer.
7. Keep the phone and watch close together until validation and reboot finish.

Do not extract the DFU ZIP before giving it to Gadgetbridge.

## Recovery

- Before PineForge is confirmed, a restart lets MCUBoot roll back to the
  previous image — reachable from the firmware screen or by holding the side
  button for two seconds.
- To start the bootloader's minimal InfiniTime recovery image, hold the
  physical side button during boot until the boot logo turns red.
- Connect to that recovery image over Bluetooth and install a known-good
  InfiniTime or PineForge DFU ZIP.

## Verification

The release asset contains:

- `manifest.json`
- `pineforge-image.dat`
- `pineforge-image.bin`

The `MCUBoot` image is byte-reproducible: rebuilding this commit yields the same
`pineforge-image.bin`. The archive around it is not, because `adafruit-nrfutil`
records file timestamps in the ZIP, so every packaging run produces a different
archive hash. Check the archive against the asset published with this release,
and the image against the value a rebuild reproduces.
