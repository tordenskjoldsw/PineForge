# PineForge v1.14.0 - The Watch Reports Back

> [!CAUTION]
> Flashing may leave a sealed PineTime unusable or require recovery. A sealed watch has no exposed SWD pads, so an image that neither boots nor reaches the bootloader's recovery path can only be waited out until the battery runs flat. Keep an official InfiniTime DFU package available and read the installation and recovery instructions before flashing.

[v0.6.1](v0.6.1.md) taught the screen to move. This release is about the other direction: what the watch measures now leaves it. Steps and heart rate reach a companion over the services InfiniTime defines, and a notification finally arrives with the name of whoever sent it.

Settings survive the update. The stored record is still version 6 and no field moved, so nothing is reset and no migration runs. BLE bonds are untouched and re-pairing is not required - though pairing afresh is worth doing once, for a reason under **What the phone caches** below.

Which build a watch is running is not stated here, because it cannot be: these notes are written before the image is packaged, and a hash quoted in advance is a hash that will be wrong. `build-dfu.sh` puts the exact commit into the firmware itself, and the About screen shows it beside the version - that answer is correct by construction rather than by anyone remembering to update a line.

## Why the version jumped from 0.6.2 to 1.14.0

This is the surprising part, so it goes first: the number is not cosmetic and it is not vanity. Gadgetbridge reads the firmware revision the watch reports and changes what it sends back accordingly.

Below 0.15 it builds a notification as the message body alone. The sender is discarded on the phone, before anything is transmitted - which is why a message used to arrive on this watch showing the text and not who wrote it. From 0.15 it sends the sender and the body together, separated by a NUL, which is exactly the shape this firmware's notification parser has always split on. Nothing in the parser changed; the number did.

Weather is the second gate and the reason the number went past 1. Gadgetbridge sends nothing below 1.8, a CBOR-framed form between 1.8 and 1.13, and a simple binary form from 1.14. This firmware reads the simple form, so 1.14 is the first number at which weather can arrive and be understood.

So the release number is now a protocol field, and `build.rs` treats it as one. It refuses a release below 0.15, where notifications would silently lose their sender again, and it refuses the 1.8 to 1.13 window, where a phone would frame weather a way this firmware cannot read and say nothing about it. Both directions are checked on every build.

There was a second version bug behind this, and it is worth naming because it looked like something else entirely. The watch had been reporting its full package version, `0.6.2+8`. Gadgetbridge splits that on dots and calls `Integer.parseInt` on each part with nothing around it, so the trailing `2+8` threw, and the line below - the one that registers the watch and its firmware in Gadgetbridge's database - never ran. What that looked like from the outside was every activity sample failing to save with a null device id. The Device Information Service now carries the release alone; the full version still names the package and still shows on the About screen.

## Steps reach the phone

InfiniTime's motion service is now declared, with the one characteristic anything reads: the step count, as a little-endian `u32` of steps taken so far today. Gadgetbridge subscribes to it on connect.

The second half of making that correct is the day boundary. The count belongs to the sensor, and the sensor has no calendar - without a reset the "day's steps" every gauge divides against the goal is really the count since the last boot, and it only ever climbs. A companion reads the value as steps *so far today* and stores the difference against what it already holds, and the branch that ends a day only runs when the watch reports a zero. Sending a number that never returns to zero would have it record a whole lifetime's walking as one day's.

So the display task notices the date change on a tick and asks the motion runner to reset the counter, and the runner publishes the resulting zero at once rather than waiting for the next ordinary read. The rule worth stating is that the first date the watch learns is never a rollover: a watch boots with the counter at zero and usually without knowing the date at all, so treating the first one as a new day would throw away every step taken since switching on.

The counter is also read while the watch sleeps now, every thirty seconds. It was not before, and that was the whole bug rather than an optimisation: a watch sleeps twenty seconds after the last touch, which is essentially all of the walking it is meant to be counting, so a companion got one sample per wake. InfiniTime reads it ten times a second whatever the watch is doing, under a comment saying why.

The raw X/Y/Z characteristic InfiniTime declares beside the count is deliberately absent. Gadgetbridge has the line that would subscribe to it commented out against its own issue 2527, so declaring it would cost attribute-table RAM for something nothing reads.

## Heart rate reaches the phone

The measurement already existed - the HRS3300 driver, the PPG processor and the pulse application were all in place - and had no way out. It now goes out on the standard Heart Rate Measurement characteristic, two bytes as the specification defines them with the flags clear, which is also exactly what InfiniTime sends.

Only validated results are published, and only changes. What a session does on the way - starting, collecting, giving up on ambient light - is a thing to draw on the watch; the characteristic has no way to express it, and a phone charting a zero would be charting a sensor that was not there. Nothing is pushed on connect either, because a rate is a moment rather than a standing value: the sensor is off between sessions and the last reading may be hours old.

## The weather arrives

`InfiniTime`'s Simple Weather service is declared, and the application is on the second page of the launcher. The phone writes the current conditions and a five-day forecast to one characteristic, and both now reach the screen. They are separate writes and a phone may send either alone, so they are held apart and drawn independently: a screen that waited for both would be blank in the common case where only one arrived.

The screen has the rhythm the pulse and steps applications have - a label, one number set large, context under it - with the location as the label where the phone sent one. The condition is one of nine 24x24 symbols, matching the set the wire format enumerates, and the bottom fifth carries the five days as a symbol over each maximum. A word would read better one at a time - `THUNDERSTORM` is never a guess where a small symbol is - but a forecast column is 48 pixels wide and no face on this watch fits a condition into it. The condition the phone could not map takes the cloud rather than a symbol of its own; a sun drawn for weather nobody identified would be a claim.

The location is drawn in the reading face rather than the instrument one, alone among the applications' labels. Theirs are constants this firmware writes and the FORGE face carries `U+0041..=U+005A`, which is enough for a word chosen here. A place name is not: it arrives from the phone in whatever case its weather service uses, and in that face `Bad Oldesloe` comes out as `B    O`. It is also cut by characters rather than bytes, so a long name spelled with an umlaut is not sliced through the middle of one.

Temperatures below zero are drawn from the same seven segments every other number on this watch is built from - the minus is the middle stroke alone, in a place of its own so a reading does not shift sideways as it crosses zero.

Reading the packets is `pineforge-state`'s, and it refuses more than it accepts: a truncated packet, an unknown message type, a version whose layout is not this one, a day count larger than the packet carries. A packet read at the wrong offsets would put a confident wrong temperature on the screen, which is worse than no weather.

## A battery application

The charge, whether it is going up or down, and the cell voltage behind both. The three charger states, the voltage formatting and the partial redraw pass host tests; the percentage itself is the capacity estimator's, which has never been compared against a reference discharge.

## The launcher is ordered by use

The list pages four at a time, so the first page is the one that costs no swipe - and it held SETTINGS, FIRMWARE and ABOUT, the three things touched once a month, while steps and music sat two pages back.

Now STEPS, PULSE, MUSIC and LIGHT lead, then TIMER, STOPWATCH, BATTERY and BLUETOOTH, then SETTINGS with the clock editors and ABOUT. FIRMWARE is last and alone on its page: it is the rarest, and the only one that changes what the watch will boot.

## The pulse screen stopped flickering

Every new reading redrew all 57,600 pixels for a two-digit change, because the screen compared the whole session state and `Result(72)` to `Result(73)` is a difference. It is also the only kind of difference that changes nothing else on the screen, so it now repaints the three digit cells and leaves the rest alone. 16,968 pixels instead of 57,600, which matters because continuous measurement produces a new value every few seconds and the application holds the watch awake.

## The runners became a crate

`src/services/` was justified by testability and never delivered any. The firmware crate is `no_main` and depends on `embassy-nrf`, so `cargo test` could not build it at all - there was not one test under `src/`, and there could not have been. What held the layer boundary instead was a grep for the string `embassy_nrf` inside that directory, which a runner reaching the chip through a GPIO driver would have walked straight past.

The sensor runners and the two bus drivers they use now live in `crates/pineforge-services`, which does not depend on embassy-nrf or embassy-executor, so cargo checks what the grep could not. Each runner takes its IPC endpoints as an argument rather than reaching for a static, which is what makes a host test able to hand it channels of its own - and there are host tests now, driving the heart-rate runner against a table of register answers with no watch involved.

## RAM, and two regressions worth publishing

`flip-link` puts the stack below the statics, so the 65,528-byte region is shared and every byte of static RAM is a byte the stack does not get. The deepest path this firmware has is a BLE key exchange, because the controller runs the elliptic-curve arithmetic in a high-priority interrupt nested over whatever the thread was doing.

Twice during this release a static-RAM change pushed the stack under what that needs, and both times the watch rebooted on every pairing attempt while every gate stayed green. The budget that should have caught it was inherited as a design target rather than derived from anything, and it permitted statics 672 bytes past a point already known to fail.

It is measured now: 16,900 bytes, read from a diagnostics build reporting its own high-water mark. Getting that reading right takes one precaution that is easy to miss and cost a shipped image - the bond lives in external flash and survives a DFU, so flashing a build and reconnecting runs no key exchange at all, and an earlier reading taken that way was three and a half kilobytes short. The phone has to forget the device first.

The reserve is 18 KiB against that peak, and the transition scratch came down from twelve rows to six to pay for it. A slide composes in forty stripes rather than twenty; the picture is identical.

## What the phone caches

Adding a GATT service to a firmware does not, by itself, make a bonded phone notice. Android caches the attribute table for bonded devices, and trouble-host declares no Service Changed characteristic and no database hash, so there is nothing to tell it otherwise.

If steps or heart rate do not appear, remove the watch in the phone's Bluetooth settings - not only in the companion app - and pair again. That is also the only way to exercise the pairing path this release spent so much effort on.

## Not established

The midnight reset has never been observed across an actual midnight, and a companion's daily accounting depends on receiving that zero. Only the on-demand heart-rate path has been seen reaching a phone, not the background interval. Neither the step count nor the heart rate has been compared against any reference.

The weather screen has shown a live record on the watch, but only the conditions half: what has been sent from a phone since is the same conditions packet, and no forecast has reached hardware. The symbols and the forecast row were checked by rendering the screen off the watch and looking at the result, which settles the layout and the glyphs and says nothing about the panel. A temperature below zero and a location longer than the label were checked the same way, host-side.

The stack peak under DFU is unmeasured, because the reboot a completed update performs clears the mark before anything can read it; part of the reserve is held for it.

Everything here was established on one sealed PineTime, one bootloader version and one phone. `docs/TESTED-CONFIGURATIONS.md` records which paths have actually been run and which have not.

## Sizes

The production image is 452,608 bytes of the 475,104-byte slot, with 46,188 bytes of static RAM against a ceiling of 47,096.
